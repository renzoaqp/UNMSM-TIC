# 2.7 Metodología / Enfoque Propuesto

## 2.7.1 Diseño de la investigación

La investigación adopta un enfoque de diseño y evaluación de artefactos, coherente con la metodología *Design Science Research* (DSR), cuyo propósito es construir y evaluar soluciones tecnológicas destinadas a resolver problemas relevantes de una organización o dominio [1], [2]. En este trabajo, el problema abordado es la limitada explotación analítica de los registros históricos de incidencias provenientes de la central de videovigilancia del Callao. El artefacto propuesto es un sistema de apoyo a decisiones para movilidad inteligente, sustentado en una arquitectura lógica independiente de tecnología y una arquitectura de referencia implementable sobre Amazon Web Services (AWS).

El proceso metodológico se organiza en cinco etapas: adquisición de datos, preparación, análisis, generación de indicadores y apoyo a decisiones. La prueba de concepto desarrollada en Kaggle implementa las primeras cuatro etapas con el conjunto de datos abierto del Callao y permite verificar la factibilidad del flujo analítico. La arquitectura AWS extiende dicho flujo hacia un escenario institucional escalable, manteniendo separación de responsabilidades y capacidad de evolución desde procesamiento *batch* hacia *near real-time*. Esta separación concuerda con las recomendaciones de AWS para diseñar cargas analíticas mediante componentes desacoplados, gobernables y escalables [3], [4].

## 2.7.2 Arquitectura lógica

La arquitectura lógica se define mediante los siguientes componentes:

1. **Fuentes de datos:** archivos CSV publicados en la Plataforma Nacional de Datos Abiertos, APIs institucionales y, en una evolución futura, eventos generados por sistemas de monitoreo.
2. **Adquisición:** recepción, identificación y registro de los datos, preservando el archivo original y sus metadatos.
3. **Preparación:** validación de estructura, limpieza, normalización, transformación y generación de variables derivadas.
4. **Analítica:** cálculo de métricas temporales, espaciales y operativas.
5. **Motor DSS:** interpretación de los indicadores y aplicación de reglas de priorización.
6. **Visualización:** presentación de mapas, tablas, tendencias y alertas.
7. **Usuarios:** actores operativos, tácticos y estratégicos.

Esta arquitectura no depende de un proveedor específico. Su finalidad es mantener estable el modelo funcional aunque cambien los mecanismos de ingestión o los servicios tecnológicos. La arquitectura física sobre AWS constituye una instancia implementable de este modelo lógico y no modifica la definición funcional del DSS.

## 2.7.3 Arquitectura de referencia AWS

La arquitectura de despliegue se propone sobre AWS y sigue principios de arquitectura analítica moderna, en los que el almacenamiento del *data lake*, el catálogo de metadatos, la preparación, la consulta, el repositorio relacional y la visualización se mantienen como capacidades separadas [3], [4]. ### Capa de adquisición

En el escenario *batch*, los archivos CSV se depositan en Amazon S3. El archivo original se conserva en una zona **Raw** para asegurar trazabilidad y permitir reprocesamiento. La carga puede ser manual durante una prueba de concepto o automatizada mediante una tarea programada.

Para una evolución *near real-time*, la arquitectura incorpora Amazon API Gateway para recibir eventos desde APIs institucionales, Amazon EventBridge como bus de eventos y AWS Lambda para validaciones ligeras y persistencia inicial. Esta distribución evita concentrar en una sola función la ingestión, el procesamiento analítico y la lógica del DSS. El uso de componentes desacoplados responde a las prácticas de diseño de cargas analíticas descritas en el AWS Well-Architected Data Analytics Lens [3].

### Capa de almacenamiento

Amazon S3 actúa como *data lake* y se organiza en tres zonas:

- **Raw:** conserva los datos originales sin modificación.
- **Clean:** almacena registros validados, normalizados y corregidos.
- **Curated:** contiene conjuntos enriquecidos y preparados para analítica y consumo por el DSS.

Esta organización separa evidencia original, datos procesados y productos analíticos. Además, facilita auditoría, reprocesamiento y reproducibilidad. AWS reconoce el *data lake* como componente central de una arquitectura moderna de datos y recomienda desacoplar el almacenamiento de los distintos mecanismos de procesamiento y consumo [4].

### Capa de preparación y catálogo

AWS Glue Crawler detecta el esquema de los archivos y registra sus metadatos en AWS Glue Data Catalog. Los *crawlers* pueden explorar datos almacenados en Amazon S3, inferir esquemas y crear o actualizar tablas en el catálogo [5], [6]. AWS Glue ETL ejecuta los procesos de limpieza, transformación y enriquecimiento.

Las reglas de calidad incluyen validación de coordenadas, conversión de fechas y horas, normalización de categorías, tratamiento de valores faltantes, eliminación de duplicados y generación de variables derivadas. La limpieza y normalización se ubican en esta capa porque deben ser reproducibles y reutilizables. La arquitectura evita implementar el ETL completo en Lambda, reservando esta función para tareas de corta duración y bajo acoplamiento.

### Capa analítica

La capa analítica consume los datos curados y genera agregaciones por hora, zona, base de monitoreo y ubicación. Amazon Athena puede utilizarse para consultas SQL directamente sobre los datos en S3 utilizando los metadatos del AWS Glue Data Catalog [7]. Cuando se requieren consultas relacionales, trazabilidad de decisiones o acceso estructurado desde aplicaciones, Amazon RDS for PostgreSQL almacena indicadores, reglas y resultados del DSS.

RDS no reemplaza al *data lake*. Su función es actuar como repositorio operacional y relacional para información curada, indicadores calculados y auditoría de decisiones. Esta separación evita utilizar PostgreSQL como almacenamiento indiscriminado de archivos y mantiene responsabilidades diferenciadas entre persistencia de objetos, consulta analítica y gestión relacional.

### Capa de decisión

El motor DSS constituye una capa lógica independiente. Consume indicadores y aplica reglas explícitas, por ejemplo:

- priorizar zonas con mayor concentración de incidencias;
- identificar franjas horarias críticas;
- detectar bases de monitoreo con mayor carga operativa;
- ordenar puntos de intervención según frecuencia, recurrencia y criticidad;
- generar resúmenes diferenciados para usuarios operativos, tácticos y estratégicos.

La primera versión emplea reglas determinísticas y métricas descriptivas, coherentes con la naturaleza de la prueba de concepto. No se atribuyen capacidades predictivas ni prescriptivas que no hayan sido implementadas. Una evolución posterior podría incorporar modelos predictivos o análisis multicriterio sin modificar la arquitectura lógica.

### Capa de visualización

Amazon QuickSight se propone para tableros institucionales, análisis exploratorio y visualización de indicadores. Los mapas de calor, marcadores y capas geográficas demostrados en Kaggle constituyen evidencia de factibilidad funcional. QuickSight se plantea como servicio de visualización y no como sustituto del motor DSS; la decisión se genera en la capa que organiza indicadores y reglas, mientras el tablero comunica los resultados.

## 2.7.4 Flujo batch

El flujo *batch* corresponde al escenario actualmente validado:

1. Descarga o carga del CSV publicado por la entidad.
2. Registro del archivo en la zona Raw.
3. Identificación del esquema y metadatos mediante Glue Crawler.
4. Ejecución del proceso ETL.
5. Escritura de datos validados en la zona Clean.
6. Generación de variables derivadas y dataset Curated.
7. Cálculo de indicadores.
8. Aplicación de reglas del DSS.
9. Publicación de tableros y mapas.

Este flujo es adecuado cuando la entidad publica datos periódicamente y no existe una fuente continua de eventos.

## 2.7.5 Evolución near real-time

La evolución *near real-time* no modifica la arquitectura lógica. Cambia únicamente el mecanismo de adquisición:

1. Los sistemas externos envían eventos mediante una API.
2. API Gateway autentica y recibe las solicitudes.
3. EventBridge desacopla productores y consumidores.
4. Lambda valida el evento y lo persiste.
5. Los eventos se incorporan al mismo modelo de almacenamiento.
6. Las capas de analítica, DSS y visualización continúan operando con los mismos conceptos.

La arquitectura distingue *near real-time* de tiempo real estricto. La propuesta no procesa video en vivo ni garantiza latencias determinísticas. Su objetivo futuro sería incorporar registros de incidencias con baja demora, conservando la capacidad de análisis histórico.

## 2.7.6 Preparación de datos

El preprocesamiento implementado en la prueba de concepto comprende:

- validación de coordenadas geográficas;
- normalización de fecha y hora;
- selección de registros de Tránsito y Seguridad Vial;
- extracción de hora, día y otras variables temporales;
- estandarización de zonas y bases operativas;
- tratamiento de registros inválidos o incompletos;
- generación de campos requeridos para mapas y agregaciones.

La secuencia se documenta para garantizar reproducibilidad. Los datos originales no se sobrescriben y cada transformación produce una nueva versión trazable.

## 2.7.7 Indicadores del DSS

El DSS utiliza los indicadores respaldados por el conjunto de datos y la prueba de concepto:

- número total de incidencias válidas;
- distribución de incidencias por hora;
- distribución por zona operativa;
- distribución por base de monitoreo;
- concentración espacial de eventos;
- identificación de zonas y horarios con mayor incidencia;
- tiempo de atención, cuando la calidad y completitud del campo permiten su uso.

Estos indicadores se organizan según nivel de decisión:

- **Operativo:** situación actual, zonas con mayor carga y distribución por base.
- **Táctico:** patrones horarios y territoriales para asignación de recursos.
- **Estratégico:** tendencias, priorización de intervenciones y evaluación de necesidades.

## 2.7.8 Validación mediante prueba de concepto

La prueba de concepto fue desarrollada en Kaggle utilizando el conjunto de datos abierto del Callao. El notebook implementa adquisición, limpieza, transformación, análisis exploratorio, visualización cartográfica y generación de capas. Esta evidencia valida la factibilidad técnica del flujo de datos y de los indicadores, pero no equivale a un despliegue productivo sobre AWS.

La validación del trabajo se plantea en dos niveles, siguiendo el principio de DSR según el cual el artefacto debe evaluarse con relación al problema que pretende resolver [1], [2]:

1. **Validación funcional:** comprobación de que el flujo procesa el dataset y genera indicadores y visualizaciones coherentes.
2. **Validación arquitectónica:** evaluación de coherencia, separación de responsabilidades, escalabilidad y capacidad de evolución del diseño AWS con respecto a las prácticas del AWS Well-Architected Framework [3].

## 2.7.9 Amenazas a la validez

La validez de constructo puede verse afectada si las incidencias registradas no representan de manera completa la movilidad del Callao. La validez interna depende de la correcta interpretación de categorías, coordenadas y variables temporales. La validez externa es limitada porque el caso corresponde a una ciudad, un periodo y una fuente institucional específicos. La validez técnica está condicionada por el hecho de que la arquitectura AWS es una propuesta de referencia y no un despliegue productivo medido. Finalmente, la calidad y frecuencia de actualización de los datos abiertos pueden limitar la oportunidad de las decisiones.

Estas limitaciones se reconocen explícitamente para evitar generalizaciones no sustentadas.
